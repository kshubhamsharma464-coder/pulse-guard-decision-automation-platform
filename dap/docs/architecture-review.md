# Architecture Review — Folder Structure & Tradeoffs.md vs. Problem Statement

**Verdict up front:** the layering is sound Clean Architecture and the Tradeoffs.md reasoning is defensible entry by entry — this would read well to a reviewer. But checked line-by-line against what's already committed to in `schema.sql` / `rules-seed.json` / `decision-engine-design.md`, there are real gaps (modules with no home) and real inconsistencies (Tradeoffs.md describes a simpler system than the one already designed, in three places). None of it is fatal; all of it is fixable before you start writing code. Details below, organized so you can act on them.

## 1. Layering — what's correct

`domain/` holding entities + interfaces (ports) + services + value objects, with `infrastructure/` implementing those interfaces, is textbook Hexagonal/Clean Architecture and matches the goals we already committed to in the design doc: domain-agnostic core, swappable persistence, testable business logic without a database. `core/dependency_injection.py` as the composition root that wires domain interfaces to infrastructure adapters is the right mechanism for that. `application/use_cases/` as thin orchestration over domain services is correct — and the apparent redundancy between `evaluate_incident.py` and `application/orchestrator.py` actually resolves cleanly once you notice `simulate_rules.py` needs the *same* pipeline (context → classify → evaluate → resolve → compliance → score → execution plan) but must not persist a decision. Factoring that shared sequencing into `orchestrator.py`, with `evaluate_incident.py` and `simulate_rules.py` as two thin callers that differ only in "persist or don't," is a good use of the pattern, not duplication. Worth stating that explicitly in the docs so it doesn't look accidental to a reviewer.

## 2. Structural gaps — things we already designed that have no home in this tree

**The Context Aggregation Layer is named in Tradeoffs.md #10 ("Context Service") but doesn't exist in the folder tree.** This is the most concrete gap. We spent real design effort on 14 named source systems (weather API, CRM, SLA system, power grid API, security alerting, vendor KB, workforce/dispatch, social listening, competitive intel, etc.), each with its own timeout and fallback, feeding `degraded_context` and `confidence_score`. That's not a detail — it's pipeline step 3 of 10. It needs an explicit home: a `domain/interfaces/context_provider.py` port, one adapter per source under `infrastructure/external/` (e.g. `weather_provider.py`, `crm_provider.py`, `power_grid_provider.py`...), and a `ContextAggregationService` (domain or application layer) that fans out to all of them in parallel with per-source timeout and circuit-breaker, not sequentially. As drawn, the tree implies this either doesn't exist yet or is buried inside `infrastructure/external/` undifferentiated — call it out explicitly.

**There is no background-job layer, and the design already requires one.** Two mechanisms we documented are time-based sweeps, not request-handlers: the SLA-breach sweep (§6, checks open decisions at 80% elapsed) and the escalation chain (§6.7, fires on acknowledgment *silence*, not on incident attributes). Neither fits into `interfaces/api/` or a use case triggered by an HTTP request. The tree has no `jobs/`, `workers/`, or `scheduler/` directory anywhere. Same gap applies to shadow-mode diffing (§8: running a draft rule pack against N live incidents in parallel and diffing before promotion) — that's also a background process, not a synchronous API call. Recommend adding a `jobs/` (or `infrastructure/scheduler/`) directory with at minimum `sla_breach_sweep.py`, `escalation_sweep.py`, and `shadow_mode_diff_runner.py`.

**The staged rule-pack lifecycle is under-represented in `use_cases/`.** The design commits to `draft → validated → shadow → active → deprecated → rolled_back` (§8), with validation meaning a JSON-schema check *and* a JsonLogic dry-run against historical incidents *and* a static `conflictsWith` contradiction check. The folder tree only lists `create_rule_pack.py` and `activate_rule_pack.py` — there's no `validate_rule_pack.py`, no `promote_to_shadow.py`, and no `rollback_rule_pack.py`, even though rollback is explicitly promised elsewhere ("single write via `parent_version_id`," edge case #29). If `activate_rule_pack.py` is meant to silently do validation-then-shadow-then-activate internally, say so — otherwise a reviewer will reasonably ask where the shadow-mode safety net you're advertising actually lives in the code.

**Manual override and escalation have no domain entities or use cases.** `domain/entities/` lists `rule`, `rule_pack`, `decision`, `incident`, `audit` — five entities against eleven schema tables. `manual_overrides` and `escalation_events`/`escalation_policies` are two of the more distinctive, NOC-credible pieces of this design (§6.6, §6.7) and currently have no entity, no repository interface, and no use case (`override_decision.py`, `acknowledge_escalation.py` are both missing from `use_cases/`). If these stay unmodeled, they'll either get bolted on awkwardly later or quietly dropped from the implementation while remaining in the pitch — worth deciding now which.

**No incident intake surface, and no incident repository.** `interfaces/api/` lists `decision_router`, `rule_router`, `simulation_router`, `health_router` — nothing that receives an incoming incident from an OSS monitoring system. Either `decision_router.py` secretly doubles as incident intake (submit incident → get decision back), which conflates two different resources under one name, or there's a missing `incident_router.py`. Given edge case #12 explicitly calls for async/bulk queue-based ingestion for storm scenarios, a queue consumer under `infrastructure/messaging/` (`incident_consumer.py`) belongs here too, alongside the outbound notification publishing that `messaging/` already implies. Relatedly, `domain/interfaces/` has no `incident_repository.py` — only `rule_repository`, `decision_repository`, `audit_repository`. That matters because an incident can exist without ever producing a decision (validation failure → manual review queue is edge case #1), so `Incident` needs a persistence lifecycle independent of `Decision`, not one folded silently into `decision_repository`.

**`engine/rule_loader.py` needs a scope boundary drawn explicitly.** Putting the JsonLogic evaluators (`engine/evaluators/`) in a top-level, domain-agnostic module is a genuinely good choice *if* `engine/` never imports anything telecom-specific — that's exactly what makes the "swap the rule pack, reuse the platform for utilities/logistics/banking" claim in the design doc true rather than aspirational. But `rule_loader.py` is ambiguous: if it means "parse a JSON condition tree into an evaluable structure," it belongs in `engine/`. If it means "fetch the active rule set for region X from Postgres," that's an infrastructure concern and putting it in `engine/` breaks the purity the whole module exists to preserve. Recommend renaming to make the boundary unambiguous (`engine/rule_parser.py` for the pure version) and adding an import-linter/dependency-direction check to CI so `engine/` importing from `domain/` or `infrastructure/` fails the build, not just a code review comment.

**Transaction boundaries aren't visible.** A single `evaluate_incident` call writes a decision, its matched/rejected/suppressed rule trace, an audit log entry, and possibly an `incident_links` row — and the entire pitch of this platform is "complete, trustworthy audit trail." If `decision_repository`, `audit_repository`, and (once added) `incident_repository` each commit independently, a failure partway through produces exactly the inconsistent audit trail the platform promises never to have. Recommend an explicit `UnitOfWork` port (`domain/interfaces/unit_of_work.py`) wrapping the use case's writes in one transaction, backed by `infrastructure/database/session.py`.

**`alembic/` appears twice** — once as `infrastructure/database/migrations/` and once as a top-level `alembic/`. Pick one; having both reads as an unresolved merge rather than a deliberate choice. Top-level `alembic/` is the more conventional default and requires less custom `env.py` wiring.

## 3. Tradeoffs.md vs. the design we already agreed on

Three of the twenty-three entries describe a simpler system than the one already specified elsewhere in this project. These are worth fixing before this doc goes in front of a reviewer, because an architect who's read both documents will notice the mismatch immediately.

**#4, Conflict Resolution** lists "Weighted Score" as a *future enhancement*, rejected for now in favor of "Highest Priority." But the design already implements both, deliberately, as two different signals: categorical `priority` resolved by weight/specificity/recency (deterministic, for safety-critical hard-stops) *and* an additive `riskScore` with LOW/MEDIUM/HIGH/CRITICAL banding (§3c, `contribution_score` column already in `schema.sql`), used for triage ranking. This isn't a nitpick — it's one of the more sophisticated pieces of the design, and the current wording throws it away as unbuilt. Fix: reframe #4 as "categorical priority for the decision, additive score as a parallel triage signal — not either/or," and explain *why* score alone was rejected as the primary priority driver (a Critical-band incident whose individual signals only sum to 40 points must still be Critical; summation would dilute a hard-stop rule).

**#12, Rule Versioning** gives the lifecycle as `Draft → Published → Deprecated → Rollback` — no `Shadow` state. The shadow-mode safety net (run a draft rule pack against real traffic in parallel, diff against the active decision, before promotion) is one of the concrete answers to "how do you stop a bad rule change from reaching production," and it's already promised in §8 and reflected in `rule_sets.status` (`draft | validated | shadow | active | deprecated | rolled_back`) in the schema. If the simplified four-state version in Tradeoffs.md is what actually gets built, the shadow-mode promise quietly disappears. Fix: either update #12 to the full six-state lifecycle, or explicitly note that shadow mode is a phase-2 item — but don't let the two documents silently disagree.

**#13, Confidence Score** defines it as "calculated from rule weights, priority, match percentage, business impact" — i.e., a measure of how strong the rule *consensus* is behind a decision. The design's `confidence_score` (§6, §9 edge case 28, `decisions.confidence_score` in schema) means something different: the fraction of context sources that returned live data vs. fell back to a default — a measure of input *data quality*, not decision strength. These are both legitimate, useful numbers, but they answer different operator questions ("can I trust the inputs?" vs. "how strong is the rule agreement?") and conflating them under one field will produce a number nobody can interpret correctly. Fix: keep `confidence_score` as data-completeness (matches the schema already written) and, if the rule-consensus number is also wanted, name it separately (e.g. `decisionStrength`) with its own formula.

## 4. Tradeoff entries worth adding

The doc is missing entries for three or four of the design's actual differentiators — the things that separate this from a generic rules engine, which is exactly what Tradeoffs.md is supposed to sell to a reviewer:

- **Suppression vs. self-veto vs. compliance constraint.** Three distinct mechanisms exist on purpose (a suppressor rule that fires and can itself be overridden; an `exceptions` self-veto that removes a rule from consideration entirely; a `COMPLIANCE`-family constraint that runs after resolution and narrows execution without competing for priority). Worth its own entry explaining why one mechanism wasn't enough.
- **Execution plan / sequencing vs. flat parallel actions.** A flat OR-merge of boolean actions can't express "try remote restart, fall back to dispatch after 15 minutes" — that needs an ordered plan with retry semantics (§3d). Worth stating as a deliberate complexity trade: more moving parts, but it's what makes the output usable by an actual ops console instead of just a label.
- **Manual override as an append-only record vs. in-place mutation.** The automated decision is never overwritten — the override is a separate, fully audited record referencing it. Directly reinforces the audit-trail selling point and deserves its own line.
- **Escalation as a background time-based sweep vs. a synchronous rule.** It fires on acknowledgment *silence*, which structurally can't be a JsonLogic condition on the incident payload — worth explaining, since it's also the reason a `jobs/` layer needs to exist (§2 above).

Also worth resolving explicitly rather than leaving implicit: **cache invalidation on rule-pack activation is TTL-based** (§5/§17 in Tradeoffs.md), which means for a stateless, horizontally-scaled API (§15) there's a window — up to one TTL period — where different replicas evaluate the same incident against different rule-pack versions. For most business rules that's a fine trade for simplicity. For a rule pack published *in response to an active incident storm* (the scenario R017 exists for), that propagation delay is arguably the worst possible moment for inconsistency. Worth either documenting the accepted delay explicitly (e.g. "≤10s TTL, deemed acceptable because...") or adding a pub/sub invalidation push (Postgres `LISTEN/NOTIFY` or Redis pub/sub) for immediate cross-replica cache-bust on activation, and stating why you picked one over the other rather than leaving it as an unstated assumption.

## 5. The one honest scope question

Six top-level source layers (`core`, `domain`, `application`, `infrastructure`, `interfaces`, `engine`) plus `tests`, `docs`, `docker`, `scripts`, `alembic` is legitimately correct enterprise structure, and it's what a Deutsche Telekom-style reviewer will expect to see. It is also a lot of wiring — DI bindings, DTOs, repository interfaces, use cases — to stand up before you can demo the actually-interesting part of this project, which is the 35-rule conflict resolution, execution plan, and compliance pass. If this is being built under a deadline, the pragmatic sequencing is: keep every layer boundary in the docs and the tradeoffs narrative (that's what gets evaluated in the writeup), but build the critical path first — `domain/services/policy_engine.py` + `conflict_resolver.py` running directly against the seeded JSON rules with an in-memory/fixture repository — and backfill the full DI wiring, real Postgres repositories, and the `jobs/` sweep layer once the core decision logic is demonstrably correct. Building all six layers evenly before the rule engine itself works is the most common way this kind of structure eats a deadline.

## 6. Prioritized fix list

Before implementation starts, in order of how much they'd embarrass the design if a reviewer caught them first:

1. Fix Tradeoffs.md #4 (score already implemented, not future), #12 (restore Shadow state), #13 (define confidence_score precisely, distinct from rule-consensus strength).
2. Give the Context Aggregation Layer an explicit module — it's named in #10 but structurally absent.
3. Add the missing use cases (`validate_rule_pack`, `promote_to_shadow`, `rollback_rule_pack`, `override_decision`, `acknowledge_escalation`) and their entities/repositories.
4. Add a `jobs/`/scheduler layer for the SLA-breach sweep, escalation sweep, and shadow-mode diff runner.
5. Resolve the `alembic/` duplication and clarify `incident_router` vs `decision_router` responsibilities.
6. Add the four missing tradeoff entries (§4 above) and state the cache-invalidation propagation-delay decision explicitly.
